Jaspersoft ISV/OEM Embedding — Architecture Overview

API structure · white-labeling · multi-tenancy model

This is the reference architecture for embedding Jaspersoft (JasperReports Server Professional/Enterprise) inside a SaaS or commercial application — the model an ISV/OEM uses to deliver analytics to their end customers under their own brand, with each customer's data isolated.

1. The big picture — three planes

PlaneWhat lives hereOEM concern
PresentationYour app's UI; embedded reports/dashboards/Ad HocWhite-labeling, seamless UX
Integration/APIVisualize.js, REST v2, SSO/token authHow your app talks to JRS
Platform / dataJRS server, repository, datasources, organizationsMulti-tenancy, isolation, scale

The defining principle: your application is the system of record for identity and tenancy; JasperReports Server is a headless analytics service that your app authenticates into and renders inside its own pages. End users should never see the native JRS login or know the server exists.

2. API structure — the integration surface

Jaspersoft exposes four integration layers, from richest/most-seamless to most-raw:

2a. Visualize.js — the primary OEM embedding API

A JavaScript framework (<server>/client/visualize.js) that renders reports, dashboards, Ad Hoc views, and input controls directly into a DOM element in your page — no iframe required.

  • Programmatic control: run, refresh, pass params, export, hook events, drill, pagination
  • Renders the content only — your app supplies all surrounding chrome
  • Cross-origin: serve your app from a different origin than JRS; CORS is governed server-side by the domainWhitelist setting
  • This is the recommended path for a polished, fully-branded embed
<script src="http://JRS_HOST/jasperserver-pro/client/visualize.js"></script>
<div id="report"></div>
<script>
visualize({ auth: { /* token or login */ } }, function (v) {
  v.report({ resource: "/reports/tenantA/sales", container: "#report",
             params: {...}, events: { reportCompleted: ... } });
});
</script>

2b. REST v2 API — server-to-server control plane

The HTTP service backing everything in the toolkit (/rest_v2/...). Used by your backend, not the browser, for:

  • Provisioning: organizations, users, roles, attributes, permissions, resources (deploy reports/datasources/Domains)
  • Execution: reports/{uri}.{fmt} (sync) and reportExecutions (async, for large fills)
  • Lifecycle: export/import (promote tenant content dev→prod), jobs (schedule), alerts
  • Auth: HTTP Basic or session cookie; ideal for automated tenant onboarding

2c. Embedded iframe / HTTP endpoints

The classic, lowest-effort embed: an <iframe> to a report URL, or a direct /rest_v2/reports/{uri}.pdf link. Simple but exposes more native chrome and is harder to brand — a fallback, not the OEM-preferred route.

2d. JasperReports Library (in-process embedding)

Embed the open-source engine directly in your Java app (no server) — fill a .jasper against a Connection and export. Suits report generation (PDF/XLSX) inside an app, but gives you none of the server platform (no multi-tenancy, scheduling, self-service). Use when you only need document generation.

Decision rule: Visualize.js for interactive embedded analytics → REST v2 for backend provisioning/automation → Library only for pure in-app document rendering.

3. Authentication & SSO for embedding

The OEM challenge: users authenticate against your app, then need to reach JRS without a second login. Options, in order of OEM-fitness:

MechanismHow it worksWhen
Token-based SSO (pre-auth)Your app sends a signed/encrypted token (shared secret); a JRS auth filter validates it, maps to a user/org/roles, and auto-provisions on first sightThe OEM standard — single sign-on, JIT user creation
Encrypted login paramsVisualize.js auth with credentials encrypted via the server's public keyQuick embed where you hold per-tenant creds
External auth (LDAP/AD, SAML, OAuth, CAS)JRS delegates auth to your IdPEnterprise SSO with a shared directory
HTTP Basic / sessionDirect credentialsServer-to-server REST only — never in the browser

Key OEM pattern — JIT provisioning + attribute injection: the pre-auth token carries the user's organization, roles, and profile attributes (e.g. customerId, region). JRS creates the user in the right tenant on first login and stamps the attributes, which then drive data-level security (see §5).

4. White-labeling — making JRS invisible

Branding works at two levels depending on integration choice:

4a. Full white-label (Visualize.js)

Because Visualize.js renders content only, your app owns 100% of the chrome — header, nav, fonts, buttons, loading states. There is no JRS UI to hide. This is the cleanest white-label and the reason Visualize.js is preferred for OEM.

4b. Themeing the native JRS UI (when users do reach it)

If users touch any native pages (Ad Hoc designer, dashboard designer, repository), restyle them with CSS themes:

  • A Themes/<name> folder with overrides_custom.css (+ logos, fonts) deployed per server or per organization
  • Activated at the organization level (PUT /rest_v2/organizations/{id} {"theme":"..."}) → each tenant can carry its own brand
  • Customizable: banner/logo, login page, colors, table styling, fonts
  • Takes effect immediately, no restart

4c. Chrome suppression

For iframe/URL embeds, request parameters and decorator settings strip the JRS header/toolbar/footer so only the report body shows. Visualize.js makes this moot.

OEM branding stack: Visualize.js for embedded content (your brand) + per-org CSS themes for any native touchpoints + custom logos/favicons + OEM license that grants white-label/redistribution rights (a contractual, not just technical, requirement).

5. Multi-tenancy model — the core of OEM isolation

This is where Jaspersoft's commercial value concentrates. The model is Organizations (tenants).

5a. Organization hierarchy

  • A tree of organizations (tenants) under a root; sub-orgs allowed (resellers → customers)
  • Each org gets an isolated repository sub-tree, its own users, roles, datasources, themes, and resources
  • An organization admin (ROLE_ADMINISTRATOR scoped to the org) manages only their tenant; the superuser/system admin manages the whole server
  • Created via REST: POST /rest_v2/organizations?createDefaultUsers=true

5b. Two isolation strategies

StrategyDescriptionTrade-off
Separate organizations (repository isolation)Each customer = one org with its own folders, users, contentStrong logical isolation; content duplicated per tenant
Shared content + attribute/row-level securityOne set of reports/Domains; profile attributes filter data per user/orgSingle artifact to maintain; relies on correct attribute injection

Most OEMs combine them: shared report definitions parameterized by per-tenant attributes, organized under per-tenant orgs for admin/branding isolation.

5c. Profile attributes — the data-isolation engine

Attributes set at server / organization / user scope are referenced in expressions and queries:

  • In a datasource URL/connection: {attribute('dbHost')}, {attribute('schema')} → each tenant hits its own database/schema
  • In a Domain security file / report query: WHERE customer_id = {attribute('customerId')} → row-level security, same report, tenant-scoped rows
  • Injected at SSO time from the pre-auth token, so the user cannot see another tenant's data even on a shared artifact

This is the mechanism that lets one report definition safely serve thousands of tenants.

5d. Per-tenant datasource patterns

  • Database-per-tenant: attribute-driven connection string selects the tenant DB
  • Schema-per-tenant: attribute selects schema
  • Shared DB, discriminator column: row-level filter via attribute (cheapest, most common at scale)

   End users (Tenant A, B, C...)
        |  (your branded UI)
   +----v-----------------+
   |  Your Application    |  <- identity, tenancy, billing; issues SSO tokens
   |  (web/app servers)   |
   +----+-----------+-----+
        |Visualize.js|REST v2 (provisioning, async exec)
   +----v-----------v-----+
   | JasperReports Server |  <- Enterprise: clustered, HA, load-balanced
   |  (org-isolated repo) |
   +----+-----------------+
        | attribute-driven connections
   +----v-----------------+
   | Tenant databases /   |
   | schemas / shared DB  |
   +----------------------+
  • Enterprise edition adds clustering / horizontal scale / HA behind a load balancer, plus a shared repository DB and shared/centralized caches (query result cache, Ad Hoc cache).
  • Stateless front, shared metadata DB → scale out the JRS tier as tenant/load grows.
  • Async report execution (reportExecutions) offloads large fills so the embed stays responsive.

7. OEM lifecycle & best practices

ConcernPractice
Tenant onboardingAutomate via REST: create org → roles → admin user → import a content template → set attributes/datasource
Content promotionAuthor once, export/import to promote dev→prod or seed each new tenant — the same envelope carries reports, Domains, Ad Hoc views, dashboards
VersioningKeep report/Domain definitions in source control; deploy via the scripted pipeline, not hand-clicks
SecurityLeast-privilege org-scoped roles; object ACLs; never embed superuser creds in the browser; tokens short-lived and signed
LicensingOEM/embedding rights are a contractual add-on — white-label + redistribution must be in the agreement, not just technically enabled
UpgradesTest theme/Visualize.js compatibility per release; pin the Visualize.js version to the server version

8. Summary — the canonical OEM pattern

  1. Your app owns identity, tenancy, and billing.
  2. Users SSO into JRS via a signed pre-auth token that carries org + roles + profile attributes; users are JIT-provisioned into their organization.
  3. Analytics render in-page via Visualize.js (no iframe, your brand) — native touchpoints, if any, wear per-org CSS themes.
  4. Multi-tenancy = organizations for admin/branding isolation + attribute-driven datasources / row-level security for data isolation, so shared report definitions serve every tenant safely.
  5. REST v2 automates the whole tenant lifecycle (provision, seed content, schedule, export/import).
  6. Enterprise scales the JRS tier with clustering/HA behind a load balancer.
